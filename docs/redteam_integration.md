# レッドチーム活動との連携設計

## 1. 位置づけ

sector_atks は攻撃を実行しません。脅威インテリジェンスからの技術の選定、検証計画と交戦規定（RoE）の管理、実行記録と防御側の証跡の突合、VDC の計算を受け持ちます。攻撃エミュレーションそのものは、権限を持つチームが既存のツール（CTID のマイクロエミュレーション計画、CALDERA、Atomic Red Team、社内の試験手順など）を使い、RoE に書いた範囲と期間の中で行います。

```
脅威インテリジェンス（ATT&CK・業種別の重み）
   │  build-weights / plan-candidates
   ▼
検証計画（plan.csv）と交戦規定（roe.json）   ← check-roe
   │
   ▼
承認済みのエミュレーション（外部ツール・隔離環境）── 実行記録 runs.csv
   │                                                 │
   ▼                                                 ▼
防御側（SIEM/EDR）── アラート alerts.csv・ログ logs.csv ──► match-evidence
                                                     │
                                                     ▼
                                    validations.csv（証跡つき）
                                                     │  vdc --plan
                                                     ▼
                         VDC・実施率・鮮度の負債・回帰率・優先度 → 改善・再検証
```

この分担にした理由は三つあります。
1. **安全性**：攻撃コードを公開リポジトリに置かない。実行は、停止条件とログ保全を備えた、承認済みの環境とツールに任せる。
2. **独立性**：検知の判定を、実行した側の自己申告ではなく、防御側のツールが記録したイベントで裏づける。
3. **再利用**：検証の中身は CTID などの公開されたエミュレーション計画を参照し、車輪の再発明をしない。

## 2. 交戦規定（`roe.json`、`check-roe`）

| 項目 | 内容 | 検査 |
|---|---|---|
| engagement_id, objective | 識別子と目的 | 必須 |
| authorized_by, authorization_ref | 承認者と承認記録の番号 | 必須 |
| environment | `isolated-lab` または `approved-production` | 他の値は不可。本番の場合は `production_approval_ref` も必須 |
| scope.hosts（scope.networks） | 試験してよいホスト | hosts は空にできない |
| window.start / end | 実施期間（UTC オフセット必須） | end > start |
| stop_conditions | 停止条件の一覧 | 空にできない |
| emergency_contact | 緊急連絡先 | 必須 |
| log_retention_days | 証跡の保存日数 | 正の整数 |

`check-roe` は**静的な検査**です。文書がそろっているか、記録された実行が範囲と期間に入っているかを事後に確かめるだけで、演習の最中に何かを止める機能はありません。範囲外の活動の阻止、停止条件の発動、緊急停止は、実行ツールの設定と RoE に書かれた担当者が受け持ちます。

`match-evidence` は、範囲外のホストや期間外の実行を採点しません。一件でも除外があると、既定では検証記録を書かずに終了コード 1 を返します（部分的な結果が正式な記録と取り違えられないように）。`--allow-partial` を付けたときだけ範囲内の実行を書き、状態を `partial` とします。

## 3. 検証計画（`plan.csv`、`plan-candidates`）

| 列 | 内容 |
|---|---|
| engagement_id, plan_id, plan_version | 演習 ID、計画 ID、計画の版。全行で同じ値でなければならない（必須） |
| scenario_id, step | シナリオと手順の順番（攻撃の連鎖を表す） |
| technique_id, procedure_id | 検証する技術と手順。組は一意 |
| reference | 手順の出典。例：`ctid-micro:ad_enum`、`atomic:<GUID>`、`internal:<ID>` |

`plan-candidates` は、業種別の重みの上位技術それぞれについて、CTID Adversary Emulation Library の中で該当する計画を一覧にします（`data/emulation/ctid_catalog.csv`）。分類は次の三つです。
- マイクロエミュレーション計画
- その業種のグループを模した攻撃者別計画
- その他の攻撃者別計画

一覧に載るのは計画の名前・URL・技術 ID だけで、計画の中身は含みません。

計画を `vdc --plan` に渡すと、技術ごとの分母が「計画した手順（と、その演習で計画外に実施した手順）」になります。未実施の手順は未検知として数えるので、易しい手順を一つだけ試して 100% になることはありません。

数えるのは engagement_id が計画と同じ記録だけです。記録に plan_id や plan_version があれば、それも計画と一致する必要があります。過去の演習の記録が新しい計画の「実施済み」に数えられることはなく、除外した件数は報告に表示されます。過去の結果を引き継ぎたい場合は、新しい演習で再検証してください。

## 4. 証跡の照合（`match-evidence`）

| ファイル | 必須の列 | 任意の列 |
|---|---|---|
| runs.csv（エミュレーション側） | run_id, technique_id, procedure_id, host, started_at, ended_at | prevention_claimed（旧名 prevented）, operator, tool |
| alerts.csv（SIEM/EDR のアラート） | event_id, rule_id, timestamp, host | technique_ids, run_id, action, uri, source |
| logs.csv（テレメトリ。任意） | event_id, timestamp, host | run_id, uri, source |

照合の規則（強いものから）：
1. **run_id があるイベント**は、その実行だけに結びつける（防御製品側に実行 ID やタグを渡せる場合に最も確実）。
2. run_id がなければ、同じホストで、時刻が「実行開始〜実行終了＋猶予（既定 300 秒）」の範囲にあり、ATT&CK の技術タグが実行の技術と（親技術の単位で）一致するアラートを候補にする。
3. **複数の実行に当てはまるイベント**（同じホストで時間が重なる場合）と、**技術タグのないアラート**は、自動では確定しない。その実行は `match_status=ambiguous` になり、候補の ID を `candidate_event_id` に残して人の確認に回す。`vdc` は曖昧な記録を数えない。

防御とログの扱い：
- `prevented` は、防御製品のイベントの `action` がブロック系（`blocked`、`prevented`、`quarantined`、`denied`）のときだけ true になる。レッドチームの申告は `prevention_claimed` として別の列に残し、証跡としては使わない。申告があってブロックの証跡がない場合は notes に書き、`vdc` の報告にも件数を出す。
- ログは可視性（`logged`）の根拠にだけ使い、`log_event_id` に入れる。`event_id`（アラート・ブロックの証跡）には入れない。
- verifier は、確定したアラート・ブロックかログがある行にだけ入る。曖昧な行には入らない。

出力の状態：
- 実行のたびに `<出力>.status.json` を書く。`status` は `complete`（全件確定）、`needs_review`（曖昧な実行あり）、`rejected`（RoE 外の実行があり、検証記録を書いていない）、`partial`（`--allow-partial` で範囲内だけを書いた）のいずれか。除外・曖昧・競合したイベント・どの実行にも結びつかなかったアラートの一覧も入る。
- 検証記録は一時ファイルに書いてから置き換えるので、途中まで書かれたファイルが残ることはない。
- `--plan` を渡すと、各行に engagement_id、plan_id、plan_version が入り、計画にない手順は notes に書く。

時刻はすべて UTC オフセット付きで受け取ります。異なるシステムの時刻を比べるため、オフセットのない時刻はエラーにします。出力の `tested_at` は実行開始時刻（UTC）で、同じ手順を同じ日に再実施したときの前後を決めます。

## 5. 指標の分離

| 指標 | 何が分かるか |
|---|---|
| 実施率 | 計画した手順のうち実施できた割合 |
| 検知率 D・防御率・ログ率 | 実施した手順に対する防御側の反応。防御率とログ率は証跡あり（既定）と記録上の値を並べて出す |
| 曖昧な照合 | 人の確認待ちで数えていない件数 |
| VDC（V の重みつき和） | 計画の範囲で、証跡つき・鮮度内で検知できた割合 |
| 鮮度の負債 | 検知はできていたが検証が失効した分（Σ w × 失効した検知の割合） |
| 回帰率 | 前回より検知率 D が下がった技術の割合（検知能力の低下） |
| 証跡のない検知 | 数えなかった自己申告の件数 |

鮮度の負債と回帰率を分けたので、「検知能力が落ちた」のか「検証が古くなっただけ」なのかを区別できます。
