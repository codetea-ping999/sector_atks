# 手法

## 1. 業種の推定（`sector_atks/sectors.py`）

ATT&CK のグループ（intrusion set）の記述文を文に分け、次の手順で「被害を受けた側」を表す部分だけを取り出してから、13 業種のキーワードを探します。

1. 文を帰属・動機の語句（attributed, affiliated, sponsored, linked to, on behalf of, believed to, motivated, part of など）の位置で区切る。
2. 区切った各部分で、標的を表す語（target, against, victim, compromise, intrusion, focus, breach, sectors, industries など）が最初に出た位置から、その部分の終わりまでを対象にする。

例：`The group attacked banks and is attributed to a Ministry of State Security.` からは `attacked banks and is` だけが対象になり、金融だけが付きます（政府は付かない）。帰属が先に来る文（`X is attributed to the military, and has targeted universities.`）でも、標的の部分だけが残ります。

- 「finance」「technology」「media」のような一般語は、後ろに区切り（カンマ、and、sectors、companies など）が続くときだけ業種とみなします。
- 判定の根拠は `group_sectors.csv` に三つの列で残します。`evidence`（一致した語句）、`sentence`（その語句を見つけた文の部分）、`source`（ATT&CK のグループのページ）。`group_sector_overrides.csv` で追加・削除できます。
- 誤判定しやすい書き方はテスト（`tests/test_weights.py` の `test_same_sentence_attribution_and_motive`）に固定してあります。

## 2. 重み（`sector_atks/weights.py`）

業種 s のグループ集合を G_s とすると、

```
share_s(t) = |{g ∈ G_s : g が t を使う}| / |G_s|
lift_s(t)  = share_s(t) / share_全体(t)
score_s(t) = (1 − β) × share_s(t) + β × p(t)
```

- グループが技術を使うとは、グループ自身の「uses」関係か、そのグループに帰属したキャンペーンの「uses」関係があることです。ソフトウェア経由の関係は、ソフトウェアが複数グループで共有されるため含めません。
- 既定では技術（親技術）単位で集計し、サブ技術は親に寄せます。`--subtechniques` で分けられます。
- 偵察（reconnaissance）と資源開発（resource-development）だけに属する技術は、組織の内部で検知を検証できないため既定で除きます。
- score 上位 N（既定 20）を優先集合 T とし、合計が 1 になるように正規化したものが w_t です。
- p(t) は外部の出現頻度（CTID など）を最大値で割って 0〜1 にしたもの。β の既定は 0 です。

## 3. VDC（`sector_atks/vdc.py`）

### 3.1 記録の単位

検証記録の 1 行は「ある手順をある日に試した結果」です。防御・アラート・ログは別々の事実なので、`prevented`／`alerted`／`logged` の 3 つの真偽値で持ちます。`outcome`（防御された／検知された／ログのみ／ログなし）はその既定値を決めるだけです。`prevented` はアラートもログもなしが既定です。防御された操作にアラートやログが伴うとは限らないので、あった場合は列で明示します。

同じ技術・手順の組は、基準日以前の最新の記録だけを使います。

証跡の列（run_id、rule_id、event_id、evidence_uri、verifier）も持ちます。既定では、event_id か evidence_uri のどちらかと verifier がそろった記録だけを検知・防御として数えます。数えなかった件数は「証跡のない検知」として表示します。`--allow-unverified` で自己申告も数えられますが、その場合は VDC を「検証済み」と呼べません。証跡は `match-evidence` で、実行記録と SIEM/EDR のエクスポートを突き合わせて埋めます（[redteam_integration.md](redteam_integration.md)）。

### 3.2 指標

| 指標 | 定義 |
|---|---|
| d_p | 手順 p の最新の記録でアラートが出たら 1、出なければ 0（`--count-prevented` のときは防御も 1） |
| f_p | 手順 p の最新の記録からの経過日数 a に対し、step なら a ≤ 窓（既定 90 日）で 1、それ以外は 0。exp なら 0.5^(a / 半減期) |
| n_t | 検証計画があれば「計画した手順と、計画外に実施した手順」の数、なければ実施した手順の数 |
| V_t（鮮度込みの検知率） | (1/n_t) Σ_p d_p × f_p。未実施の計画手順は d = 0。VDC の計算に使う |
| 実施率 | 計画した手順のうち実施した割合 |
| D_t（検知率） | 実施した手順に対する Σ_p d_p の割合。鮮度を無視した値。回帰率の比較に使う |
| F_t（鮮度） | 実施した手順の f_p の平均。参考値 |
| 鮮度の負債 | Σ_t w_t × (1/n_t) Σ_p d_p × (1 − f_p)。検知はできていたが検証が失効した分 |
| 防御率・ログ率 | 防御された手順、ログが残った手順の割合。ログ率を可視性と呼ぶ |
| VDC | Σ_t w_t × V_t。0〜1 の範囲を外れたらエラー |
| 申告ギャップ | ルールがあると申告した技術の重みの合計 − VDC |
| 回帰率 | `--previous-as-of` の時点で D > 0 だった技術のうち、今の D が下がった技術の割合（検知能力の低下。鮮度の失効は含まない） |
| 改善速度 | 同じ手順が検知できなかった日から、次に検知できた日までの日数の平均 |
| 優先度 | 残り = w_t × (1 − V_t)。この値が大きい技術を直すほど VDC が大きく上がる |

研究ノート 06 の式（w × D × F、F は技術の最終検証日で決める）からの変更点：F を技術単位で決めると、120 日前に成功した手順 A と今日失敗した手順 B があるとき、A の成功が今日の検証として数えられてしまいます（D = 0.5、F = 1）。手順ごとに鮮度を掛ければ、この場合 V = 0 になります。全手順を同じ日に試した場合は、二つの式は一致します。

未検証の技術は V = 0 として数えます（検証していないものは検知できると見なさない）。

検証計画がないと、分母は実施した手順の数になり、易しい手順を一つ試すだけで V = 1 になり得ます。報告にはその旨を表示します。比較や論文には計画つきの値を使ってください。

`--previous-as-of` を付けると、前回時点の VDC と鮮度の負債も表示します。VDC が下がったとき、回帰率（能力の低下）と鮮度の負債（検証の失効）のどちらが原因かを分けて読めます。

### 3.3 入力の検証

- 重み：負数、NaN、無限大、数値でない値、technique_id の重複はエラー。合計が正でなければエラー。読み込み後に合計 1 に正規化する。`compute` に直接渡す重みも、合計が 1 でなければエラー。
- 検証記録：outcome は 4 値のいずれか、真偽値の列は true/false/yes/no/1/0 のいずれか（空欄は既定値）。
- 鮮度：窓は 0 以上、半減期は正の値（`--half-life 0` はエラー）。モードは step か exp。
- 検証計画：technique_id と procedure_id の組の重複はエラー。

## 4. データの質の評価

`build-weights` は重みと一緒に次の値を出します（ATT&CK v20.0 の結果）。

| 項目 | 値 | 読み方 |
|---|---|---|
| 業種を付けたグループ | 178 中 110 | 残り 68 は `untagged_groups.csv`。記述に標的業種が書かれていないグループが多い |
| 付与あり群と付与なし群の上位 20 の重なり（Jaccard） | 0.54 | 付与できなかったグループの使う技術の傾向は、付与できたグループとある程度違う。業種別の重みは「業種が公開報告に書かれているグループ」に偏っている |
| 少数業種（グループ 15 未満） | 運輸 14、NGO 12、メディア 11、小売・宿泊・飲食 8 | `sector_summary.csv` の `low_n` 列。重みの信頼性が低い |
| ブートストラップ安定度 | 0.53〜0.75（政府が最大、小売・宿泊・飲食が最小） | 業種のグループを復元抽出し直して上位 20 を作り直したときの、元の上位 20 との重なりの平均（200 回、乱数の種は固定）。1 に近いほど、どのグループが付いたかに結果が左右されない |
| 全グループ基準との重なり | 0.38〜0.74 | 業種別の上位 20 が、業種を問わない上位 20（`weights/_all_groups.csv`）とどれだけ違うか |
| 判定規則の感度 | 0.54〜1.00（13 業種中 6 業種で 1.00、小売・宿泊・飲食が 0.54） | 標的の部分に限らず記述全体からキーワードを探す緩い規則で業種を付け直したときの、上位 20 の重なり（`sector_summary.csv` の `overlap_with_loose_rule`）。小売・宿泊・飲食以外は、判定規則を変えても上位 20 は 8 割以上同じ |

ブートストラップ安定度がどの業種でも 0.75 以下なので、上位 20 の顔ぶれのうち 3〜5 割はグループの選ばれ方しだいで入れ替わり得ます。業種別の順位は「傾向」として扱い、個々の順位を確定値として扱わないでください。

### 4.1 業種推定の抜き取り監査

`group_sectors.csv`（修正前の 303 件）から 40 件を無作為に抜き出し（乱数の種 20261107）、根拠の文を読んで判定しました。

- 正しい：37 件（適合率 約 0.93）
- 誤り：3 件
  - G0130：「defense industrial base」を製造業と判定 → パターンを修正（`industrial base` を除外）
  - G0085：「医療・製薬企業に関する金融市場の情報を狙った」を医療と判定 → 上書きファイルで削除
  - G1056：「暗号資産の窃取」（手口）を金融と判定 → 上書きファイルで削除

### 4.2 付与なしグループの抜き取り調査（再現率の目安）

`untagged_groups.csv`（68 件）から 20 件を無作為に抜き出し（乱数の種 20261108）、記述の全文を読みました。

- 16 件：記述に標的の業種が書かれていない（地域、手口、帰属のみ）。付与できないのは正しい。
- 1 件：明らかな付け漏れ。G0044（Winnti Group）の「gaming industry」。原因は、13 区分にゲーム・娯楽産業がないこと（分類体系の不足）。
- 3 件：判断が分かれる。G1026（銀行向けトロイの木馬で個人を狙う）、G0067（キャンペーン名「North Korean Human Rights」）、G1043（「critical infrastructure」。具体的な業種がない）。

付与なしのグループの多くは、ATT&CK の記述に業種の情報がないために付与できていません。キーワード規則の取りこぼしは少数です。再現率を正確に求めるには、各グループの出典レポートまで読む必要があります。分類体系にゲーム・娯楽と「重要インフラ（業種不特定）」を加えるかどうかは、今後の検討点です。

## 5. 妥当性への脅威

- 業種推定はキーワードによるもので、誤判定と漏れがある（4.1 節）。ATT&CK に載っているグループは公開報告が多いものに偏る。
- 「使うグループの割合」は報告の多さに引きずられる。実際の観測頻度（Sightings など）とは一致しない。
- 対象グループが少ない業種では重みが不安定になる（4 節）。
- d_p は手順の数で頑健性を近似しており、手順の選び方に依存する。「アラートが出た」ことと「分析者が気づいて対応した」ことは別である。
- 以上から、VDC と業種別の重みは研究上の比較・優先順位づけの材料であり、セキュリティ上の意思決定の確定指標ではない。
